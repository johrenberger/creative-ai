## src/cli.js — Interactive CLI (CTA-GAP-006)

**Decision:** Accept low Jest statement coverage for `src/cli.js` until a refactor lands.

**Current state:** 0% statement and 0% function coverage in Jest's coverage report.

**Why:** `src/cli.js` is a Node.js script with side effects at module load:
- `readline.createInterface()` is called when the module is imported
- `process.stdin` listeners are registered
- The module has no exports; it's a runnable script, not a library

Jest cannot collect coverage from a module that has no exports and executes side effects at load time. The existing `tests/cli.test.js` does test the CLI's structure (modes, command parsing, HTTP request patterns) using mocks for `readline` and `process.exit`, but those tests can't be counted toward coverage of the real module.

**Subprocess coverage (alternative):** `tests/cli.test.js` does some coverage through subprocess testing — spawning the CLI as a child process and verifying its output. That's not reflected in Jest's coverage report, but it does test the behavior end-to-end.

**Refactor path (the alternative "or" in the gap):** Make `src/cli.js` importable as a module by:
1. Wrapping the readline setup in an exported `startCLI()` function
2. Exporting the MODES structure and helper functions
3. Adding a guard so the readline setup only runs when the module is run directly (`if (import.meta.url === \`file://\${process.argv[1]}\`)`)
4. Refactoring the 4 modes (Repl, Mem, Triage, Exchange) into separate functions that can be unit-tested

**Trigger to revisit this decision:** If/when the CLI becomes a user-facing product (e.g. shipped as `npx cti`) or when a regression in CLI behavior is reported that wasn't caught by `tests/cli.test.js`'s subprocess approach.
